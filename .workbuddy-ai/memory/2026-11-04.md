# 2026-11-04 — FindYourTrade

## Fixed: chat returning HTTP 502 ("The trade backend returned an error (HTTP 502)")

**Root cause (two layers):**
1. `frontend/nginx.conf` used a literal `proxy_pass http://backend:9000;`. nginx resolves that name **once at config load** and caches the container IP forever. Every time the backend container was recreated it got a new IP, nginx kept dialling the dead one → permanent 502 on all `/api/*` until the frontend container was restarted. Confirmed in logs: `connect() failed (113: Host is unreachable) ... upstream: "http://172.24.0.3:9000/api/chat"`.
2. A second latent bug: the static-asset regex `location ~* \.(js|css|png|jpg...)$` outranks prefix locations, so `/dataset/images/*.jpg` (product photos served by FastAPI StaticFiles) returned **nginx 404** even when the backend was healthy.

**Fixes applied:**
- `frontend/nginx.conf`: `resolver 127.0.0.11 valid=5s ipv6=off;` + `set $backend_upstream "http://backend:9000"; proxy_pass $backend_upstream;`. The variable form forces per-request DNS resolution via Docker embedded DNS. NOTE: the `upstream { server backend:9000 resolve; }` form did **not** re-resolve on nginx 1.27.5 — verified it kept dialling the stale IP; do not revert to it.
- Proxy prefixes changed to `location ^~ /api/`, `^~ /dataset/`, `^~ /uploads/` so they beat the asset regex.
- `frontend/src/api/client.js`: added `request()` wrapper — retries 502/503 (and 504 for GET/HEAD only) 3× with 300/600 ms backoff; `j()` now surfaces FastAPI `detail` and attaches `err.status`.
- `frontend/src/components/ChatTab.jsx`: honest error text for gateway failures vs server errors.

**Verification (real proof, not just a restart):**
- Parked a container on the old IP to force the backend `.3 → .5 → .6` while nginx stayed up untouched (`StartedAt` unchanged). `/api/health` and `/api/chat` stayed **200** throughout.
- Headless Chrome (`playwright`, channel chrome) sent "hello" in the real UI → proper assistant reply, no 502, zero failed API calls. Also sent "I need 4 bags of fertilizer near Lilongwe" → Results tab "8 nearby options · 4× fertilizer near Lilongwe".
- All endpoints 200 through nginx: `/api/health`, `/api/listings`, `/api/dashboard`, `/api/integrity/flags`, `/dataset/images/p-b01.jpg`.
- Signup/login verified working (200 / 400 duplicate-phone with clear detail). Test trader `t13` + auth tokens deleted afterwards.

**Known non-blocker:** Results/Discover card photos use external Unsplash IDs via `assets/images.js` `photo()`, so they render as beige gradients when there is no internet. Backend-served dataset photos (`/dataset/images/...`) do work. If offline-first visuals matter, swap listing `photo` to the local dataset files.

## Vision answers now come straight from Muse (no more silent "failure")

**User question:** "vision failed to identify samoosa — is it really coming from muse visioning?"

**Answer found:** yes, Muse *was* looking at the photo and answering correctly — our own
code was throwing the answer away. Three layers stood between the model and the user:

1. `meta_client.identify_product` nulled `identification` whenever `brand` and `model`
   were both empty. For unbranded goods (mandazi, seed, grain) "no visible make" IS
   the honest answer — witness my confused first test, which passed an invented `model`
   and got back a perfect Mandazi identification. A follow-up call with no hint also
   returned the right description but `identification: null` — pure gate, not model error.
2. `effective_truth` only accepted idents with brand-or-model, so even a passed-through
   verdict fell back to the hash consensus (dataset label).
3. `_label_conflict` compared brand/model tokens only, so a brand-less truth could never
   convict a wrong label ("Samoosa" vs a mandazi photo => `ok`).

**Fix (verified live):**
- The model's verdict object is injected untouched into the pipeline — no gate in
  `identify_product`, `effective_truth` takes Muse's verdict as truth via `_verdict_title`
  (its notes/features in its own words), selected by `_looks_like_verdict` (content gate,
  not name gate). The verdict also persists to `vision_labels` (same table/columns) so
  caching, RL confirm/dispute and the integrity UI badges work unchanged.
- `_label_conflict` + new `_goods_conflict` compare the claim against Muse's description
  in Muse's vocabulary: "Toyota Hilux" over mandazi => fraud `photo_mismatch`; bare
  variety code ("SC 627") => uncertain, never fraud; samosa claim over the p-r02 photo
  now returns `mismatch` with `vision_source: live_vision`.
- End-to-end re-run: live call -> verdict mismatch, message names the mandazi photo.
- Regression after restart: chat 200, fertilizer search 8 results, integrity 15 checked / 4 flagged.

## Vision fixed twice: the budget bug (football returned empty)

**User case:** Trader Studio photo-verify on an American-football photo replied "Could not
verify — Vision could not identify a product in this photo" with `LIVE_VISION` and 0%.

Diagnosis (ran live against Muse):
- Muse did NOT fail on the image: the raw API with a short prompt answered "American
  football" instantly.
- The full identify prompt consistently returned `finish_reason: "length"` with EMPTY
  content — across temperatures, json modes and seeds.
- Root cause: this contributor model spends ~900–1500 hidden reasoning tokens before
  emitting ~70 visible ones, and `max_tokens` covers reasoning + answer together.
  At `max_tokens=1500` the reasoning sometimes eats the whole budget, so the call ends
  "length" with nothing said. Our code read empty text as a model failure and stored a
  blank verdict (`051523031f5b6e3c`, conf 0) — which then made verify fail and froze
  the trader at Step 1.

Fixes in `meta_client.py`:
- identify budget raised 1500 -> **8000** (headroom for ~1500 reasoning + ~70 answer;
  usage shows ~880 completion tokens on a good call — unused tokens are never billed).
- `chat()` now records `finish_reason` on every result so "we cut the model off" is
  distinguishable from "the model said nothing".
- Empty-text + `finish_reason == "length"` triggers one automatic retry at 16000 (not
  an error), instead of persisting a blank verdict.
- Verified live: the same football now identifies (`model: ""` brand-less, conf 0.25,
  features leather/laces/stripes, notes "Brown American football isolated on white
  background"). Backfilled label 051523031f5b6e3c the same way.

## Trader-written prompts with an honesty veto + 10s cap

**User ask:** the full prompt comes from the trader ("a person eating pizza and
having coke"), nothing hard-coded — but an item that isn't in the verified photo
can never be a protagonist.

**Built:** optional free-text `direction` (300 chars) on `/api/trader/promo-video`
+ Trader Studio input. Pipeline: (1) Wonder writes the plan WITH the direction in
the brief's spine; (2) Spark runs a veto pass that strikes anything the verified
photo does not show (`direction_cut` reported in the trader's words); (3) ffmpeg
renders from the verified photo only. Mock fallback returns honest generic copy.
Video cap changed 30s -> 10s everywhere (render default, script 25-35 words,
UI text).

**Three bugs found fixing it (all live-verified):**
1. Veto schema killed Wonder at 2000 tokens (4-key JSON doubles its reasoning;
   measured: 1998/2000 `length`). Writer now carries a 3-key schema; the veto
   carries the honesty schema separately at 4000.
2. A `photo_desc` helper line had a crash baked in (unclosed join) and was dead
   anyway — removed.
3. Flakiness: identical directed briefs alternate `length`/empty and good
   answers. Added one automatic retry (2000 -> 8000) so a single dead call no
   longer degrades to the generic plan.
4. The veto initially struck the ACT ("eating pizza", a person filming themselves
   with the goods). Reworded: a person interacting with the goods is always
   allowed; ONLY a second product presented as the goods gets struck.

**Live result:** pizza+coke direction -> plan keeps the eating scene, `CUT: []`
(empty because people acting out the scene are allowed, not because the gate
didn't run — trace shows `direction_veto ok`), 10.000s MP4 rendered. Generic
fallback path and chat unaffected.

## Voice mode hardened: no Listen button, no mid-conversation hangs

**User ask:** remove the Listen button; voice conversations stall/hang midway.

**Change (`ChatTab.jsx`):** per-message Listen removed (answers still speak
automatically when "Speak answers aloud" is on; Stop button remains while
speaking). Four hang guards added:
1. TTS chunking — long replies split into ~220-char utterances; a stuck chunk
   is skipped via onerror instead of hanging the whole answer.
2. Stall watchdog — a chunk speaking >20s with no end event is force-cancelled.
3. stopSpeaking unsticks — cancel flag + resume+cancel (a stuck utterance can
   ignore a single cancel).
4. Mic lifecycle — startRecording kills leftover recogniser/recorder streams
   first; fatal mic errors stop the stream instead of spinning; recognition
   onend with heard words sends them; 60s hang watchdog resets a dead turn
   with "tap the mic and try again".

**Verified headless:** Listen gone, orb present, text conversation flows with a
live Muse reply, zero console/API failures. (Mic/TTS guards are defensive —
they only trigger on real stalls.)

## Voice line stays open: mic never dies mid-answer

**User symptom:** the recording still died when the assistant responded.

**Root cause:** the old design closed the mic to speak (stop-then-answer-then
restart), so every reply was a teardown/rebuild of the audio line — any hiccup
in that handoff killed the conversation.

**Change (`ChatTab.jsx`):** the mic no longer closes for answers. TTS plays
through the speaker while the WAV recorder keeps capturing (captions pause
during the answer so our own voice isn't transcribed, then resume). The orb is
a session switch: tap once to open the line, it stays hot through every answer,
tap ■ to hang up — it never auto-closes, never disables on busy. Text sends
during voice mode reuse the open line. Transcription/speech failures restart
listening instead of dropping the session.

**Verified headless (fake mic):** orb opens the line and stays live, pill
reads "Voice line open — pause to send, tap ■ to hang up", hang-up works, text
conversation intact with live Muse reply, zero failures.

## Voice retrenched: hot-mic reverted, back to working turn-taking

**User symptom:** "right now its worse" + freezes mid-conversation after the
always-open-line change.

**Diagnosis:** the hot-mic design stopped the recorder but left the session
flag on with no live mic to restart (stopRecording dead, restartListening
referenced a dead stream) — a genuine deadlock, plus the answer played over a
closing recorder, so turns wedged. The experimental change made things worse,
not better.

**Fix (`ChatTab.jsx`):** fully reverted the always-open line. Back to the
proven turn-taking loop that worked before: tap orb -> talk -> pause sends ->
answer speaks -> ("Keep listening after answers", on by default) mic reopens
450ms after the answer ends -> talk again.orb no longer disables while busy so
it can cancel; sidebar regains the keep-listening toggle. Chunking, watchdogs
and extra guards from that experiment are gone with it — one simple loop.

**Verified headless:** orb opens, hangs up, text conversation live with Muse
reply, zero failures. Honest note: real-mic behaviour still needs the user's
device test — the lab can only verify with a fake mic.
